## 2026-09-19 (40)
- **`hdd-music` (WD Green 2TB, `sdc1`) hardware failure — root cause found and worked around, drive itself not yet replaced.** Timeline: kernel `ata11` link exceptions started 13 Sep (5 days before `nhdl` was even deployed), escalated during heavy sustained write I/O from `nhdl`'s batch downloads today, ending in a full journal abort + EXT4 shutdown + kernel dropping the disk entirely (`DID_BAD_TARGET`). Investigation ruled out: SATA cable (reseated), SATA port (moved), M.2-to-5-port-SATA expansion card (LM 418, JMicron JMB585 — briefly fell off PCIe entirely after a cable-handling session, reseated in the M.2 slot, confirmed back in `lspci`), and Molex power cable (swapped). Root cause narrowed to the drive itself: it links at the SATA layer but historically failed the `IDENTIFY` handshake (`failed to IDENTIFY, err_mask=0x80`) — a controller-board/mechanical-level fault, not a link/cable issue. **Important discovery: this same failure mode hangs the whole Proxmox host at BIOS/POST for 5+ minutes if the drive is connected at power-on** (unclear why — device stuck in a bad state the BIOS's SATA scan doesn't time out on gracefully) — host boots normally in seconds with the drive disconnected. Hot-plugging the drive after the OS is already up is safe and doesn't reproduce the hang. Once hot-plugged post-boot this time, the drive surprisingly identified successfully and mounted read-only with the `music/` library (723GB) intact and readable, though it hard-reset once under sustained read load before stabilizing — data is accessible but the drive should be treated as failing, not fixed. Mounted **read-only** at `/mnt/hdd-music` (both on `pve` and passed through to `docker-host`) specifically to avoid triggering more journal writes on an unstable drive. **`nhdl`'s missing `list.txt`/`library.json`/queue state from earlier today is a separate, permanent loss**: that state lives only in the container's writable layer (see (25)/(26)'s known limitation), and got wiped by the 2 container recreates done during today's routine updates — unrelated to the hardware failure, not recoverable.
- **Reconfigured `nhdl`'s `DOWNLOAD_DIR`** from `/mnt/hdd-music/download/nhdl` to `/downloads-temp` (bind-mounted from `/opt/projects/nhdl-downloads-temp` on `docker-host`'s root SSD), since `hdd-music` is read-only/unstable and can't be written to right now. Root SSD has 60GB free, user confirmed expected usage is under 10GB so this is safe short-term (per `CLAUDE.md` storage convention this would normally be wrong — bulk downloads belong on HDD — but it's a deliberate, small, temporary exception while `hdd-music` is down).
